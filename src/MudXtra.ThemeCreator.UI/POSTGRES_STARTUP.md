# PostgreSQL startup guard

The final Docker stage starts `/bin/sh /app/docker-entrypoint.sh`. It invokes the same application assembly with `--postgres-probe` and the same command-line/configuration inputs. Probe mode returns before registering/building app services: authentication plus exactly `SELECT 1`, with no EF context, ThemeCreatorService, initialization or migration. Built-in Npgsql type metadata avoids extra catalog queries. No extra OS package is required; the script is read by `/bin/sh`, so executable permissions are unnecessary.

Exit contract: `0` ready; `10` transient/attempt timeout; `20` permanent configuration/authentication/database/query/TLS-policy failure; `130` shutdown. Exceptions and connection strings are never printed. SQLSTATE class28, database3D000, other SQL/config/permissions failures fail immediately; only connection class08, shutdown/not-ready57P01/02/03, capacity53300 and transient transport timeouts retry. Unexpected query results fail closed.

Proposed defaults: **10 seconds total per probe process**, **six attempts**, **five 60-second waits**. Six attempts allow five recovery windows (~six-minute maximum guard budget: 6×10 + 5×60 =360 seconds, excluding process scheduling overhead). The shell starts each wait only after the transient probe process exits, never after permanent failure or final exhaustion. There is no nested retry loop. A hard process-level deadline also bounds the driver's separate cancellation handshake/disposal; returning exits the process and the OS closes residual sockets. Normal successful probes dispose their Npgsql command/connection/data source. TERM/INT stop/reap the shell's active child or sleep; `exec` replaces the shell only after readiness.

Bare app startup verifies once before building/serving, with the same process deadline/shutdown behavior. This single check adds at most10 seconds, not another retry budget. It is intentional protection against guard-success/database-loss races. EF registration is deterministic required validated `UseNpgsql`, with no connection test or `UseSqlServer`/LocalDB fallback. Subsequent database loss can still fail app operations; the guard is not a runtime health/readiness oracle and does not make those operations succeed. The shell does not retry/restart a subsequently failing application.

## Activation / rollback boundary

This is a staged source/Docker candidate, **not a live installation**. Do not copy this entry script into the running October2025 image: that assembly does not contain the probe mode. Do not activate by running the existing app against production to test readiness. The deployed image contains October initial migration20251007155012_Initial while the database history contains four February/March migrations. Binary identifier evidence alone is not model/schema compatibility proof. Existing `ThemeCreatorService` initialization/automatic `Database.Migrate` is unchanged and remains a separate live activation gate.

Before activation, independently verify the exact reviewed image's model/schema/migration compatibility under explicitly authorized migration policy, retain the exact previous immutable image/config/entrypoint and deployment rollback materials, and stage the reviewed candidate without touching database/data/provider settings. Rollback is restoring that previous immutable image/config/entrypoint; it is **not** DB rollback, migration application, mutable-latest upgrade or provider switching. This patch changes no migrations or schema and authorizes none. Visual Studio fast/debug base-stage execution bypasses the final shell but still uses the bare app's single-attempt fail-closed check.
